### Data Management Terms
- **ACID Properties**: Atomicity, Consistency, Isolation, Durability - properties that guarantee database transactions are processed reliably   - **BASE Properties**: Basically Available, Soft state, Eventual consistency - alternative to ACID for distributed systems   - **CAP Theorem**: States that it is impossible for a distributed data store to simultaneously provide more than two out of the following three guarantees: Consistency, Availability, Partition tolerance   - **Eventual Consistency**: Consistency model used in distributed computing to achieve high availability   - **Strong Consistency**: Guarantees that any read operation returns the most recent write for a given piece of data   - **Causal Consistency**: Guarantees that writes that are causally related must be seen by all processes in the same order   - **Read-After-Write Consistency**: Guarantees that after a record has been updated, any attempt to read it will return the updated value   - **Monotonic Read Consistency**: Guarantees that if a process reads the value of a data item x, any successive read operation on x by that process will always return that same value or a more recent value   - **Monotonic Write Consistency**: Guarantees that the system will serialize writes by the same process   - **Consistent Prefix**: Guarantees that if a sequence of writes happens in a certain order, then anyone reading those writes will see them appear in the same order   - **Sharding**: Database partitioning technique that separates very large databases into smaller, faster, more easily managed parts   - **Replication**: Process of sharing information to ensure consistency between redundant resources   - **Master-Slave Replication**: One device (the master) controls one or more other devices (the slaves)   - **Master-Master Replication**: Each node can both read and write   - **Multi-Master Replication**: Database replication method where data can be stored by a group of any number of computers, and any member of the group can update the data   - **Shard Key**: Determines how data is distributed across shards   - **Consistent Hashing**: Special kind of hashing such that when a hash table is resized, only k/n keys need to be remapped on average   - **Partitioning**: Division of a database into distinct independent parts   - **Vertical Partitioning**: Splitting a table by columns   - **Horizontal Partitioning**: Splitting a table by rows   - **Materialized View**: Database object that contains the results of a query   - **Index**: Data structure that improves the speed of data retrieval operations   - **Bitmap Index**: Special type of index that uses bitmaps   - **B-Tree Index**: Self-balancing tree data structure that maintains sorted data and allows searches, sequential access, insertions, and deletions   - **Hash Index**: Index that uses a hash table   - **Full-Text Search**: Techniques for searching a single computer-stored document or a collection in a full-text database   - **Inverted Index**: Index data structure storing a mapping from content to its locations in a database file   - **Denormalization**: Process of attempting to optimize the read performance of a database by adding redundant data or by grouping data   - **Normalization**: Process of organizing data in a database   - **First Normal Form (1NF)**: Requires that the domain of each attribute contains only atomic values   - **Second Normal Form (2NF)**: Meet all requirements of 1NF and remove redundant data   - **Third Normal Form (3NF)**: Meet all requirements of 2NF and remove columns that are not dependent on the primary key   - **Boyce-Codd Normal Form (BCNF)**: Slightly stronger version of 3NF   - **Fourth Normal Form (4NF)**: Meet all requirements of BCNF and remove multi-valued dependencies   - **Fifth Normal Form (5NF)**: Deal with join dependencies and is free from join dependency   - **Domain-Driven Design (DDD)**: Approach to developing software for complex needs by connecting the implementation to an evolving model   - **Bounded Context**: A boundary within which a particular model is defined and applicable   - **Ubiquitous Language**: Language structured around the domain model and used by all team members   - **Entity**: Object that is fundamentally defined not by its attributes, but by a thread of continuity and identity   - **Value Object**: Object that contains attributes but has no conceptual identity   - **Aggregate**: Cluster of domain objects that can be treated as a single unit   - **Aggregate Root**: Entity that controls access to a cluster of objects   - **Factory**: Object for creating domain object that creates other objects for use within the domain   - **Repository**: Mechanism for encapsulating storage, retrieval, and search behavior   - **Service**: When a domain concept doesn't naturally fit as an Entity or Value Object   - **Module**: Another way of organizing the code, with the goal of reducing related concepts or using the code as a means of reducing coupling   - **Domain Event**: Something that has happened in the domain that you want other parts of the domain to be aware of   - **Event Sourcing**: Ensures that all changes to application state are stored as a sequence of events   - **CQRS (Command Query Responsibility Segregation)**: Separates the read and update operations for a data store   - **Eventual Consistency**: Consistency model used in distributed computing to achieve high availability   - **Saga Pattern**: Sequence of local transactions where each transaction updates the database and publishes a message or event   - **Orchestration-based Saga**: Centralized coordinator (orchestrator) tells each participant what local transaction to perform   - **Choreography-based Saga**: Participants exchange events without a centralized coordinator   - **Polyglot Persistence**: Using different data storage technologies to handle varying data storage needs   - **Cache-Aside Pattern**: Loads data on demand into a cache from a data store   - **Read-Through Cache**: Cache that is responsible for reading data from the data source   - **Write-Through Cache**: Write is made to the data store and to the cache   - **Write-Behind (Write-Back) Cache**: Write is done only to the cache   - **Refresh-Ahead Cache**: Proactively loads the latest value for a key into the cache before its expiration   - **LRU (Least Recently Used)**: Evicts the least recently used items first   - **LFU (Least Frequently Used)**: Evicts the least frequently used items first   - **FIFO (First In, First Out)**: Evicts the first item that was added to the cache   - **Random Replacement**: Randomly selects an item to evict   - **Time-Based Expiration**: Invalidates items after a certain time period   - **Cache Stampede**: Occurs when a cache expires and multiple clients simultaneously try to reload the same data   - **Cache Invalidation**: Process of removing entries from a cache   - **Write-Through**: When data is written to the cache, it is also written to the backing store   - **Write-Behind**: When data is written to the cache, the write to the backing store is delayed   - **Write-Around**: Similar to write-through, but writes bypass the cache and go straight to the backing store or persistent storage   - **Read-Through**: When data is requested and not found in the cache, it is loaded from the data store into the cache   - **Cache Aside**: Application is responsible for reading and writing from the data store   - **Memcached**: High-performance, distributed memory object caching system   - **Redis**: In-memory data structure store, used as a database, cache, and message broker   -
